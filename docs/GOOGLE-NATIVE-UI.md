# Gmail / カレンダー / 連絡先 — 専用UI 設計

> 現在この3つは Google の Web ページをそのまま表示しています。これを **Google API を叩いて
> DeskHatch が自前で描く UI** に置き換える設計。
>
> **結論から**: カレンダーと連絡先は実現可能。**Gmail だけは審査の壁が別格**で、
> 配布形態によっては年額費用と年次セキュリティ監査が必要になります。
> 先に「2. 実現可能性」を読んでから、作るかどうか判断してください。

---

## 1. なぜ専用UIか

| 現状の問題 | 専用UIでどうなるか |
|---|---|
| ドロワーは幅360〜600px。Google の Web UI は本来その幅を想定していない | 幅に合わせて自前で描くので破綻しない |
| 埋め込みブラウザだとサインインがブロックされる（`disguise.js` の存在理由） | トークン認証。ブラウザの偽装が不要になる |
| Chromium のバージョンが古いと「サポート終了」バナーが出る | 無関係になる |
| ページ全体の読み込みが毎回走る | 必要なデータだけ取得。体感が段違い |
| 「今日の予定だけ見たい」のに月表示が出る | 用途に合わせて設計できる |

逆に失うもの: **Google の全機能**。設定変更、複雑な検索、添付の編集などは
結局 Google を開くことになります。**専用UIは「よく使う操作の近道」**であって、
Google の置き換えではない、という前提で設計します。

## 2. 実現可能性（ここが本題）

Google API を使うには OAuth クライアントが要ります。そこに**スコープの区分**という壁があります。

### スコープの区分と、かかるコスト

| | スコープ区分 | 本番公開に必要なもの |
|---|---|---|
| **カレンダー** | Sensitive | Google の審査（無料、数日〜数週間） |
| **連絡先 (People API)** | Sensitive | 同上 |
| **Gmail** | **Restricted** | 審査 **＋ CASA セキュリティ監査**（有償・**毎年**更新） |

CASA の費用は第三者業者の2026年時点の公開情報で **年 540〜1,500 USD 程度**。
Google 公式の価格表ではないので、やるなら必ず最新を確認してください。

**ローカルアプリだから免除、はありません。** Google のポリシーは
「本番環境で Restricted スコープを使う全アプリ」が対象です。

### Testing モードの落とし穴

「審査を受けずに Testing モードで使えばいい」は、**7日でリフレッシュトークンが失効**します。
つまり**週に1回ログインし直し**。常用するバーのボタンとしては実用に耐えません。

公開ステータスを **In production** にすればトークンは長命になります。
自分ひとりで使う分にはこれで回りますが、

- 未審査のまま production にすると、初回に「Google はこのアプリを確認していません」の警告画面が出ます（1回通せば以後出ない）
- Sensitive スコープの未審査アプリにはユーザー数の上限があります（**要確認**: 検索では確定情報が取れませんでした。Google の OAuth 確認ドキュメントで裏を取ってください）

### これが意味すること

```
自分（と身内）だけで使う
   → カレンダー・連絡先・Gmail すべて可能
   → production + 未審査（警告を1回通す）

DeskHatch の正式機能として配布する
   → カレンダー・連絡先: 審査を通せば可（無料）
   → Gmail: CASA 監査が毎年必要。個人アプリには重い
```

**Gmail だけ扱いを分けるのが現実的**です。

## 3. アーキテクチャ案（3つ）

### 案A: DeskHatch に直接組み込む

```
DeskHatch
 ├ src/main/google.js      OAuth（PKCE＋ループバック）／トークン保管／API中継
 └ src/renderer/           Gmail・カレンダー・連絡先のパネルを自前描画
```

- ✅ 最短。追加プロセスなし
- ❌ **DeskHatch 本体が Restricted スコープを持つアプリになる**。Microsoft Store や winget で配る以上、CASA の対象になりうる
- ❌ OAuth クライアントIDがアプリに同梱される

### 案B: コンパニオンアプリにする（**推奨**）

さきほど実装した **ローカルアプリ連携プロトコル**（`docs/LOCALAPP-PROTOCOL.md`）をそのまま使います。

```
DeskHatch                      DeskHatch Google Panel（別アプリ）
 └ type:'localapp' ドロワー ──▶ http://127.0.0.1:PORT/calendar
                                 ├ OAuth クライアントを所有
                                 ├ トークンを OS キーチェーンに保管
                                 └ Gmail/Calendar/People API を叩く
```

- ✅ **DeskHatch 本体は Google の資格情報を一切持たない**。審査の対象外のまま
- ✅ 入れる人だけが入れればいい。Gmail 連携を使わない人に影響なし
- ✅ **すでに作った仕組みがそのまま使える**。DeskHatch 側のコード追加はゼロ
- ✅ 名刺管理アプリ・書類管理アプリからも同じパネルを再利用できる
- ❌ 別アプリを作る手間（ただし DSBooks と同じ作り方）

### 案C: Gmail だけ分離

カレンダー・連絡先は案A（本体組み込み・審査は無料）、Gmail だけ案B。

- ✅ 日常の価値が高い2つを本体の標準機能にできる
- ❌ 2つの仕組みを保守することになる

### 推奨: 案B

理由は「**DeskHatch 本体を Google の審査レーンに乗せない**」の一点です。
本体が Restricted スコープを持った瞬間、ストア配布と CASA 更新が毎年ついて回ります。
コンパニオンに切り出せば、本体はただのビューアのままでいられます。

そして案B なら、今日作った `localapp` の仕組みの**2例目**になります。
DSBooks で証明した型がそのまま効くかの検証にもなります。

## 4. 認証の設計（案B前提）

### 方式: OAuth 2.0 Authorization Code + PKCE + ループバックリダイレクト

デスクトップアプリに「秘密にできるクライアントシークレット」は存在しないので、
**PKCE 必須**です。Google の「Desktop app」クライアント種別はこれを前提にしています。

```
1. パネルが一時HTTPサーバを 127.0.0.1:0 で立てる
2. 既定ブラウザで Google の同意画面を開く（埋め込みブラウザは不可・Googleが拒否）
3. 同意後 127.0.0.1:PORT/callback?code=... に戻る
4. code + code_verifier をトークンに交換
5. リフレッシュトークンを OS の安全な領域に保存
     Windows: DPAPI / macOS: Keychain（Electron なら safeStorage）
6. 以後アクセストークンを都度更新
```

**平文でトークンをファイルに置かないこと。** 保存前に `safeStorage.encryptString()` を通します。

### スコープ（最小権限）

| 用途 | スコープ | 区分 |
|---|---|---|
| 予定の閲覧 | `calendar.readonly` | Sensitive |
| 予定の作成・変更 | `calendar.events` | Sensitive |
| 連絡先の閲覧 | `contacts.readonly` | Sensitive |
| メール一覧・本文 | `gmail.readonly` | **Restricted** |
| 既読・アーカイブ・削除 | `gmail.modify` | **Restricted** |
| 送信 | `gmail.send` | **Restricted** |

**最初は readonly だけで作る**のを勧めます。書き込みを足した瞬間に審査の重さが変わります。

## 5. 各パネルの設計

ドロワーは縦に長く横が狭い（360〜600px）。**1画面1目的**で設計します。

### カレンダー（最優先・最も価値が高い）

```
┌────────────────────────┐
│ ◀  10月16日(木)  ▶   ＋│  日付ナビ＋クイック追加
├────────────────────────┤
│ 終日  頭痛学会（熊本）  │
├────────────────────────┤
│ 08:30 ─────────────── │
│   勤: 真和整形          │
│ 10:30 ─────────────── │
│   キッズパル            │
│ 18:30 ─────────────── │
│   プレシオ全体          │
├────────────────────────┤
│ 明日 ▸ 3件              │  折りたたみプレビュー
└────────────────────────┘
```

- **既定は「今日」**。月表示は Google を開く
- 予定タップ → その場で詳細（場所・参加者・Meet リンク）
- 「＋」→ 1行入力（`明日14時 歯医者`）→ Calendar の quickAdd API に投げる
- 複数カレンダー（個人・仕事）は色で区別、表示切替あり

### 連絡先

```
┌────────────────────────┐
│ 🔍 検索…                │
├────────────────────────┤
│ ● 山田 太郎             │
│   090-xxxx-xxxx        │
│   yamada@example.com   │
├────────────────────────┤
│ ● 鈴木 花子             │
└────────────────────────┘
```

- **検索が主役**。一覧をだらだら出さない
- 電話番号タップ → `tel:` / メールタップ → 既定メーラ or Gmail 作成画面
- ローカルキャッシュ必須（連絡先は滅多に変わらない。毎回APIを叩かない）

### Gmail（最後・審査の壁の先）

```
┌────────────────────────┐
│ 受信トレイ    未読 12   │
├────────────────────────┤
│ ● 田中さん              │
│   見積もりの件          │
│   お世話になっております…│
│                 10:24  │
├────────────────────────┤
│ ○ GitHub                │
│   [deskhatch] CI failed │
│                  9:02  │
└────────────────────────┘
```

- **未読と直近のみ**。全文検索は Google を開く
- 開く → 本文をプレーン寄りに整形して表示（HTML メールは sanitize 必須）
- 操作は**アーカイブ・既読・スター**まで。返信・作成は Google を開く
  （送信スコープを避けられる＝審査が軽くなる）
- 添付はダウンロードして既定アプリで開く

## 6. 共通の設計方針

### キャッシュとレート制限

- API のレスポンスは**必ずローカルに保存**し、起動時はキャッシュを即表示 → 裏で更新
- カレンダーは `syncToken` による差分同期が使える。全件取得を繰り返さない
- Gmail は `historyId` で差分取得
- ドロワーを開くたびに全取得すると、すぐ割り当てを使い切ります

### オフラインとエラー

| 状態 | 表示 |
|---|---|
| ネットなし | キャッシュを表示＋「オフライン（最終更新 10:24）」 |
| トークン失効 | 「再ログイン」ボタン1つ。勝手にブラウザを開かない |
| API エラー | 内容を出す。黙って空リストにしない |
| 未認証 | 「Google アカウントを接続」ボタン |

### セキュリティ

- トークンは `safeStorage` 経由でのみ保存
- HTML メール本文は **DOMPurify 相当で sanitize**、外部画像は既定ブロック（トラッキングピクセル対策）
- パネルは `127.0.0.1` のみ bind（`LOCALAPP-PROTOCOL.md` の必須要件）
- パネルのループバック API には**トークンを要求**（他のローカルプロセスから叩かれないように）
  ※ `/ping` だけは認証不要（DeskHatch のヘルスチェック用）

## 7. 段階的な進め方

```
Phase 0  Google Cloud プロジェクト作成・OAuth クライアント発行
         production に設定（7日失効を回避）              ─ 半日

Phase 1  コンパニオンアプリの骨格
         ループバックサーバ＋/ping＋OAuth(PKCE)＋safeStorage ─ 2〜3日
         LOCALAPP-PROTOCOL.md の必須4点を満たす

Phase 2  カレンダーパネル（readonly）                     ─ 2〜3日
         DeskHatch 側は SS_LOCALAPPS に1行足すだけ

Phase 3  クイック追加（calendar.events）                  ─ 1日

Phase 4  連絡先パネル（readonly＋キャッシュ）             ─ 2日

Phase 5  Gmail（readonly）                                ─ 3〜5日
         ※ ここで初めて Restricted スコープ。
           配布するなら CASA の判断が要る

Phase 6  Gmail 操作（modify）                             ─ 2日
```

**Phase 2 まで行けば、効果の大半が手に入ります。**
カレンダーが狭い幅で快適に見えるだけで、日常の体験はかなり変わるはずです。

## 8. 決めてもらう必要があること

1. **配布するか、自分用か**
   自分用なら未審査 production で全部いけます。配布するなら Gmail の扱いを決める必要があります。

2. **案B（コンパニオン）でいいか**
   推奨しますが、「DeskHatch 1つで完結したい」なら案A/Cもあります。
   その場合 DeskHatch 本体が Google の審査レーンに乗ることを受け入れることになります。

3. **どこから作るか**
   カレンダーからを勧めます。審査が軽く、API が素直で、狭い幅での改善幅が一番大きいためです。

4. **既存のドロワーをどうするか**
   専用UIができても、Google を開く導線（現状の `type:'page'`）は残すべきです。
   専用UIは近道であって置き換えではないので。
